Context

A growing logistics team needed one dashboard to replace spreadsheets — shipped in 10 days.

This is a self-initiated case study. I set myself a real-world scenario: a logistics team had outgrown spreadsheets and free tracking tools and was ready for its first custom dashboard. I designed it from scratch — one product covering what dispatchers needed, built to ship in 10 days.

Style choices

I locked the grid, type, and color system before touching a the main screen.

A 1440px grid with defined columns and gutters, one typeface at four sizes, and color tokens for light and dark mode — decided upfront, not improvised mid-build.

Rapid Prototyping

I split one long page into two dedicated screens.

V1 put everything — KPIs, charts, orders, map — on one scrolling dashboard. I split it into two screens: Dashboard for the at-a-glance summary, CRM for the order-level detail. Dispatchers checking status don't need to scroll past a table to get there, and the table gets room to actually work as a table.

Micro-interactions

I prototyped the interactions, not just the states

Light/dark mode toggle, table row hovers, slide-in panels, page-to-page transitions — all wired in Figma so it behaves like the real product, not a slideshow. A dev watching this before they build it has fewer "wait, how's this supposed to feel?" questions.

Developer Handoff

I built variables the way a developer would actually use them, not just labeled colors.

Primitive tokens hold the raw values, semantic tokens reference them by function — card/hover, font/primary brand/primary — so nothing gets hardcoded. Every state that's easy to forget (delete confirm, status badges, deltas) is spec'd too, not left for a dev to ask about later.
